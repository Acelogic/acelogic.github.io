Porting Voice Conversion to MLX on Apple Silicon

Follow the hiss and vowel in a single word through pitch estimation, feature retrieval, and synthesis on the Mac.

Miguel Cruz · November 24, 2026 · 6 min read

On this page

Say the word “see” and stretch out the vowel. The hiss at the beginning tells a listener which word you said. The vowel carries a pitch you can raise or lower while leaving the word recognizable. A voice converter has to preserve details like that hiss while generating audio with the character of the target voice. When I ported retrieval-based voice conversion to MLX for Apple Silicon, those two sounds gave me a way to reason about what each stage should carry forward.

Starting with a common clock

Consider the Python file-conversion path in the port. The loader reads samples from disk, averages the channels if the file is stereo, and resamples the signal to 16,000 samples per second. The pipeline applies a high-pass filter at 48 Hz and reflects 1,600 samples onto each end. That supplies a tenth of a second of context around both boundaries. A model processing the first vowel now has some audio to its left, just as it would for a vowel in the middle of a sentence. Audio loader and filtering and padding.

A one-second, 48 kHz stereo recording starts with 48,000 sample values per channel. After mixing and resampling, the analysis path has 16,000 mono samples. Padding brings that to 19,200. The pitch path uses a 160-sample hop, so it has a budget of 120 ten-millisecond positions in that padded input. A hop measures the distance between consecutive estimates. It does not restrict the estimator to hearing ten milliseconds of context. That distinction matters when interpreting an abrupt change in pitch at the edge of a syllable.

Two descriptions of the same vowel

The content branch sends the audio through a HuBERT-style encoder. Convolutions produce features a short distance apart, and the encoder refines them using context. Each result is a vector of learned values that helps the synthesizer recover the speech sounds. Keeping the vectors avoids having to transcribe the word, pick a dictionary pronunciation, and reconstruct the original timing from those symbols. It also means that a change to one feature coordinate rarely has a simple name like “more sibilance.” Content encoder.

The other branch estimates fundamental frequency, or F0. On a voiced stretch of “see,” the vibration of the vocal folds produces a roughly repeating pattern. If the pitch extractor reports 110 Hz, the estimated period is about 9.1 milliseconds. On the hiss, a frame may receive zero because there is no stable periodic source to track. That zero is a meaningful input to the converter. The content branch still carries the shape and timing of the consonant. The file runner uses RMVPE as its default pitch method, with other estimators selectable through the same interface. Pitch extractor interface.

Suppose I request a shift of twelve semitones with autotune disabled. The pipeline multiplies each estimate by two raised to the power of the shift divided by twelve. The 110 Hz vowel becomes 220 Hz. Zero stays zero. The code saves those continuous values and makes a second, coarse representation on a mel scale. With the port’s 50-to-1,100 Hz mapping, 110 Hz rounds to bin 23 and 220 Hz rounds to bin 60. An unvoiced frame lands at the lower bin of 1 while its continuous F0 remains zero. Those two arrays now convey different information about precisely the same frame. Transposition and pitch quantization.

Giving the frames the same addresses

The HuBERT front end takes a stride of five followed by six strides of two. Multiply those numbers and adjacent content vectors correspond to input positions 320 samples apart, or 20 milliseconds at 16 kHz. The pitch path advances twice as often. To align the two, the port repeats each content vector. Two consecutive pitch estimates can therefore accompany the same content vector. If the vowel is sliding upward, the pitch estimates can change over those two frames even though the repeated content vector stays identical. Convolution strides.

There is a small edge case hiding in those tidy numbers. The last convolution window must fit its input. Dividing the original sample count by 320 gives the spacing, but it does not establish how many complete feature vectors the convolutions produce. The implementation bounds the length using the smaller of the input’s 160-sample positions and the repeated content sequence, then trims the pitch arrays to that span. When tracking an alignment problem, I would inspect the last frame that goes into the synthesizer before blaming a pitch detector for dropping a syllable. Frame repetition and trimming.

What the retrieval dial changes

If I supply a feature index and select a positive index rate, the converter asks FAISS for eight neighboring vectors for each content frame. It squares the reciprocal of each returned distance and normalizes those weights before combining the neighbors. A neighbor with distance 1 consequently has four times the influence of one with distance 2 before the common normalization. The resulting vector is blended with the original content according to the index rate. This lookup happens before the content vectors are repeated and leaves the pitch estimates alone.

Here is the arithmetic for one imaginary coordinate. Let the original value be 0.20 and the weighted neighborhood value be 0.80. An index rate of 0.75 produces 0.65. With protection set to 0.25, a voiced frame keeps that 0.65. An unvoiced frame blends one quarter of 0.65 with three quarters of the original 0.20, yielding 0.3125. The protection branch is active for settings below 0.5. This gives the hiss more of its input features while letting the sustained vowel use the retrieved ones. The example follows one coordinate for legibility. The actual blend operates over whole vectors. Retrieval weights and unvoiced protection.

Carrying a model across frameworks

The synthesizer combines content and coarse pitch in its encoder, uses an embedding for the speaker ID, and passes a latent representation through the reverse flow. The decoder receives that representation and the continuous F0 contour to generate samples at the model’s output rate. A 40 kHz model needs 4,000 output samples trimmed at either end to remove the tenth of a second of context we added. Trimming 1,600 output samples instead would remove only 40 milliseconds at that rate. Synthesizer inference.

A checkpoint also has an ordering contract. For an ordinary one-dimensional convolution, the conversion tool moves the PyTorch axes for output channel, input channel, and kernel position into MLX’s output channel, kernel position, and input channel order. Transposed convolutions need a different permutation. If two axes happen to have the same length, a mistaken swap can pass a shape check and still connect a coefficient to the wrong channel. A short reference clip and intermediate feature values can locate that error far more precisely than an inspection of the final waveform alone. Checkpoint layout conversion.

For a listening comparison I would keep the same recording and voice model, convert once at zero pitch shift and once at twelve semitones, and listen separately to the onset and the held vowel. For timing I would also specify whether the interval includes file I/O, index retrieval, and writing the output. MLX can defer computation, so a timer around construction of an array expression captures different work from a timer that waits for the samples. One short recording can reveal all three kinds of mistake if I preserve its inputs and ask a specific question at each stage. MLX evaluation semantics.
